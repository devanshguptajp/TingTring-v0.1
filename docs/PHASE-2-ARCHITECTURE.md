# TingTring Talk (TTT) — Phase 2 Architecture

Status: DECIDED
Phase: 2
Date: 2026-09-22

## Architecture decision

TTT will be a native Android application built with Kotlin and Jetpack Compose.

### Android client
- Kotlin
- Jetpack Compose for UI
- Android Telecom self-managed ConnectionService for VoIP call integration
- Foreground/background call handling as required by Android
- FCM-compatible push delivery for waking/alerting the app for incoming calls
- LiveKit Android SDK for WebRTC media and SFU-based group calling
- Android audio routing/Bluetooth support through the platform and LiveKit
- Screen sharing through Android media projection + LiveKit screen-share track

Android Telecom officially supports standalone/self-managed VoIP apps through ConnectionService and PhoneAccount. The app will use this route for real incoming-call behavior without becoming the normal cellular phone service.

### Backend
Supabase will provide:
- PostgreSQL database
- Authentication
- Email OTP/password authentication
- Realtime where appropriate
- Storage where appropriate
- Row Level Security for user data

TTT does not use a phone number as an identity or authentication field.

### Calling/media layer
LiveKit will provide:
- WebRTC audio/video transport
- SFU-based group calling
- Room/participant management
- Screen-share media
- Reconnection/network recovery
- Media/data tracks

The TTT backend will issue short-lived LiveKit access tokens. LiveKit credentials/secrets never ship in the Android application.

### Server-side TTT API
A dedicated backend service will sit between the Android client and privileged systems.

Responsibilities:
- TTT User ID generation and uniqueness
- Username uniqueness/filtering
- Profiles
- Contacts/search authorization
- Call authorization
- Plan/entitlement evaluation
- Owner-call override
- Owner authorization
- Account deletion
- Identity reservations
- Owner Console APIs
- LiveKit token generation
- Push notification orchestration
- Audit logging
- Rate limits and abuse controls

The exact backend runtime will be finalized in Phase 5 after the database/auth requirements are validated.

## Identity model

TTT users do NOT submit a 10-digit phone number.

Each user receives a unique TTT User ID. That ID is the primary calling identity.

Separate identifiers:
1. System User ID — globally unique, generated by TTT.
2. Username — globally unique and searchable.
3. Display name — non-unique.
4. Email — authentication/recovery credential; not the calling identity.

The User ID must never be accepted as a substitute for a phone number in a phone-number field because TTT has no phone-number identity model.

## Authentication

Initial authentication direction:
- Email OTP/passwordless login
- Optional password login/recovery
- Email is for account authentication, not calling identity
- No SMS OTP requirement
- No SIM requirement

## Calls

Call flow:
1. Caller searches/selects a TTT user.
2. TTT backend verifies caller authorization and target availability.
3. Backend creates/authorizes a call session.
4. Backend sends an incoming-call push notification to the target's registered device(s).
5. Target app reports the call through Android Telecom as a self-managed incoming VoIP call.
6. Participants receive short-lived LiveKit room tokens.
7. Android clients join the LiveKit room.
8. LiveKit handles realtime audio/video/data transport.
9. TTT backend records permitted call metadata, not private call audio/content.

## Security boundaries

- Client UI is never the security boundary.
- Backend validates all privileged operations.
- LiveKit API keys/secrets remain server-side.
- Owner permissions are enforced server-side.
- User private contact names remain local unless explicitly designed otherwise.
- Owner Console cannot listen to or secretly retrieve private call audio/content.
- No AI Insights feature.
- Secrets are never committed to GitHub.

## Why this architecture

Native Android is required for the app's call behavior and platform integration. Android documents self-managed ConnectionService specifically for standalone VoIP calling applications.

LiveKit avoids building an SFU and complex WebRTC media infrastructure from scratch while still allowing TTT to control its own identity, authorization, plans, and application logic.

Supabase reduces backend setup for authentication and relational data while keeping TTT's application authorization in a dedicated backend layer.

## Phase 2 exit criteria

- Native Android architecture selected: Kotlin + Jetpack Compose
- Calling architecture selected: LiveKit/WebRTC
- Backend data/auth foundation selected: Supabase
- Dedicated TTT API boundary defined
- Android Telecom integration selected
- Phone-number identity removed from architecture
- No secrets or production credentials stored in repository
